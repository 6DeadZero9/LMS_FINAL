## 1. Use Case та постановка задачі

**Use case:** indoor mobile robot (TurtleBot3 Burger) — лабораторна платформа для оцінки сенсорної фільтрації пози на плоскій підлозі.

**Сценарій роботи:** Робот у симуляторі Gazebo стартує в `(0, 0)` і один раз проїжджає квадратний маршрут 2×2 м між чотирма відомими віхами (стовпами), після чого зупиняється. Паралельно EKF оцінює позу за IMU, колісною одометрією та LiDAR; GUI порівнює чотири комбінації сенсорів з ground truth Gazebo (ATE / yaw RMSE).

## 3. Sensor Allocation Table

| # | Сенсор | Модель | Призначення | Апаратний інтерфейс | ROS-топік | Частота (Hz) | Вартість ($) |
|---|--------|--------|-------------|----------------------|-----------|--------------|--------------|
| 1 | IMU | Gazebo IMU plugin (аналог MPU на OpenCR TB3) | \(a_x\), \(\omega_z\) для predict EKF; yaw bias | I²C до MCU на платі керування | `/imu` | ~200 | ~10–20 (на платі) |
| 2 | Wheel odometry | DiffDrive + квадратурні енкодери | Body linear speed \(v\) (не поза) | Квадратурні імпульси → лічильник на MCU | `/odom` | ~30 | ~0 (входить у привід) |
| 3 | 2D LiDAR | LDS-01 (HLS-LFCD) | Range/bearing до 4 відомих стовпів | USB (внутрішньо UART-to-USB) | `/scan` | ~5 | ~90–120 |

*Ground truth винесено з таблиці сенсорів — див. підрозділ 3.1.*

**Обґрунтування вибору кожного сенсора (з альтернативами):**

1. **IMU:** обрано плату з I²C-інтерфейсом (аналог MPU6050/MPU9250 на OpenCR). Альтернатива — BNO055 з апаратним sensor fusion: точніший і менш чутливий до дрейфу, але дорожчий і надлишковий, коли фільтрація вже виконується в `fusion_node`. Для цілей курсового проекту простіший IMU з видимим дрейфом навіть кращий.
2. **Wheel odometry:** апаратна альтернатива відсутня — енкодери вбудовані в привід TB3 Burger, окремий вибір компонента тут не робиться. У фільтрі використовується лише twist \(v\), щоб не витісняти LiDAR-корекцію позиції.
3. **LiDAR LDS-01:** обрано за USB-інтерфейсом і низькою вартістю. Альтернатива — RPLidar A1 (більша дальність ~12 м, вища частота сканування), але надлишкова для кімнати 2×2 м і дорожча приблизно вдвічі; LDS-01 з дальністю ~3.5 м повністю покриває задачу.

### 3.1. Джерело еталону для валідації (не сенсор)

Ground truth поза `burger` з Gazebo Transport (`/ground_truth/odom`) використовується виключно як еталон для розрахунку ATE/yaw RMSE та для керування `path_follower` (pure pursuit). Це не фізичний сенсор системи, а симуляційний оракул — у реальній системі його роль виконував би зовнішній трекер (наприклад, Vicon), тому він навмисно виключений з Sensor Allocation Table.

## 5. Power Budget

*(Орієнтовно для реального TB3 Burger у indoor-режимі; у курсовому проєкті платформа симулюється.)*

| Компонент | Струм (мА) | Duty Cycle | мА·год/добу |
|-----------|-----------|------------|-------------|
| SBC / MCU (active, Pi-клас) | 400 | 0.3 (рух/обчислення) | 2880 |
| MCU/SBC (idle) | 150 | 0.7 | 2520 |
| IMU (на платі) | 5 | 1.0 | 120 |
| LiDAR LDS-01 | 300 | 0.5 (під час місії) | 3600 |
| Мотори + драйвер (середнє) | 800 | 0.25 | 4800 |
| WiFi / ROS link | 100 | 0.5 | 1200 |
| **TOTAL (середнє)** | | | **~15120** |

**Середнє споживання:** 15120 мА·год/добу ÷ 24 год ≈ 630 мА → 630 мА × 11.1 В ≈ **7 Вт**, що відповідає уточненій вимозі "~7–10 Вт середньо" в розділі 2.

**Пікове споживання (одночасний рух + сканування):** SBC active (400 мА) + LiDAR (300 мА) + мотори (800 мА) ≈ **1.5 А × 11.1 В ≈ 17 Вт**, що потрапляє в діапазон "~15–25 Вт", уточнений у розділі 2 як пікове значення.

**Розрахунковий час роботи від 1800 мА·год (типовий пак TB3 ~11.1 В):** при середньому ~630 мА → близько **2.5–3 год** безперервної місії.

## 6. FMEA (Failure Mode and Effects Analysis)

| Сенсор | Режим відмови | Ефект на систему | Severity (1–5) | Mitigation |
|--------|---------------|------------------|----------------|------------|
| IMU | Stuck / bias jump | Дрейф yaw і пози в IMU-only / без LiDAR | 4 | Оцінка \(b_g\) в EKF; LiDAR suite; synthetic bias лише в ПЗ для демо |
| Wheel odom | Slip / хибний \(v\) | Зсув швидкості, гірший predict | 3 | Великий \(R_v\); LiDAR absolute updates; не оновлювати yaw з коліс |
| LiDAR | Втрата стовпа / хибна асоціація | Помилковий update пози | 4 | Mahalanobis gate; асоціація за позою фільтра; 4 redundancy poles |
| Bridge / QoS | Немає `/imu` чи `/scan` | Порожні графіки / застигла оцінка | 5 | Sensor-data QoS; перевірка топіків після launch |
| Gazebo / spawn | Порожня сцена, немає burger | Немає GT і руху | 5 | Burger у SDF; один процес `gz sim`; `pkill` старих серверів |
| Power | Battery undervoltage | Системний reset | 5 | Voltage monitoring + graceful shutdown |

## 8. Planned Pipeline

```
[ Gazebo TB3 ] --> [ ros_gz_bridge + noise/bias ] --> [ EKF ×4 suites ] --> [ /fusion/<mode>/odom ]
        |                                                      |
        +--> [ GT pose ] --> [ pure pursuit ] --> [ /cmd_vel ]
        |                                                      |
        +--> [ dashboard: RMSE / ATE vs GT, suite select ]
```

Gazebo генерує сенсори й істинну позу. Bridge віддає їх у ROS; `fusion_node` робить predict з IMU та updates з odom/LiDAR у чотирьох режимах. `path_follower` веде квадрат за GT (оцінка не керує моторами). Dashboard показує траєкторії й RMSE та перемикає активний suite через `/fusion/selection`.
